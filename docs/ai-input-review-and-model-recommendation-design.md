# AI 입력 피드백 및 모델 추천 설계

작성일: 2026-11-24

상태: 설계 기록 완료, 구현 예정

이 문서는 사용자와 합의한 AI 입력 검토, 모델 추천, 사용자 확인 및 이력 저장의
구현 기준이다. 아래 API, 테이블, 필드는 제안이며 아직 구현된 계약이 아니다.
작업 우선순위와 진행 상태는 [루트 개발 계획](../dev_plan.md)에서 관리한다.
단계별 작업·완료 기준·검증 기록은 [구현 로드맵](ai-input-review-and-model-recommendation-roadmap.md)에서 관리한다.

## 목표와 1차 범위

사용자가 작성한 계획 입력을 AI가 먼저 검토하고, 사용자가 피드백과 적용할 가정,
선택 모델을 확인한 뒤 계획을 생성한다. 검토부터 생성 결과까지 PostgreSQL 이력으로
연결해 추천 효과와 최종 계획 품질을 평가할 기반을 마련한다.

1차 범위:

- AI 입력 검토와 핵심 보완 질문, 현재 정보로 진행할 때의 가정 표시.
- 입력 명확성, 전문지식 요구도, 추론·계획 복잡도, 작업 규모 평가.
- 서버 정책에 따른 모델 추천과 사용자의 모델 선택.
- 확인된 입력·가정·모델에 연결된 계획 생성.
- 검토·선택·확인·AI 실행 이력 저장 및 프로젝트별 조회.
- 생성 결과에 대한 간단한 사용자 품질 피드백 저장 경로.

후속 범위:

- 동일 입력에 대한 여러 모델의 통제된 비교 실행과 자동 품질 평가.
- 모델별 품질·비용 대시보드와 학습 기반 추천.
- 수집 기록의 학습 데이터 선정·익명화·내보내기 정책.

이력 수집만으로 학습을 자동 실행하거나, 사용자 입력마다 여러 모델을 호출하지 않는다.

## 현재 구조와 변경 이유

- `apps/web/src/lib/modelRecommendation.ts`는 입력 글자 수, 상황·실행 항목 수,
  제약조건 길이, 계획 유형과 성공 기준을 합산해 브라우저에서 모델을 추천한다.
  짧지만 전문적인 요청과 의미적 제약을 충분히 구분하기 어렵다.
- `apps/web/src/lib/planningInput.ts`는 상황과 해야 할 일을 하나 이상 입력해야
  생성을 허용한다. 정보가 부족한 사용자도 검토를 받을 수 있도록 검토 진입 조건과
  최종 생성 조건을 분리해야 한다.
- `RequirementPanel.tsx`의 제출은 `planningStore.ts`의 `generateResult`로 이어진다.
  이 사이에 검토·보완·확인 상태를 추가한다.
- API는 FastAPI, 저장은 SQLAlchemy·PostgreSQL, migration은 Alembic을 사용한다.
  기존 `planning_results`의 결과 버전·비교·편집·복원 구조를 유지하며 이력을 연결한다.
- `packages/ai/planning_ai/provider.py`는 구조화된 응답을 반환하지만 응답 사용량을
  저장하지 않는다. 검토와 생성 양쪽의 실행 정보 수집을 추가한다.

## 사용자 흐름

1. 프로젝트를 선택하고 계획 주제를 입력한다.
2. `AI 입력 검토`를 누른다. 주제만 있어도 검토할 수 있다.
3. AI가 이해한 목표, 명확한 내용, 보완 질문, 진행 가정과 추천 모델을 표시한다.
4. 사용자는 입력을 보완해 다시 검토하거나, 현재 정보와 표시된 가정으로 진행한다.
5. 최종 입력·가정과 선택 모델을 확인하고 `확인하고 계획 생성`을 누른다.
6. 확인 기록을 저장한 후 해당 기록에 연결된 계획을 생성한다.
7. 생성 결과에서 관련 검토·선택 이력을 조회하고 품질 피드백을 남길 수 있다.

피드백 예시:

> 이해한 목표: 직원 교육에 필요한 자료와 진행 일정을 준비합니다.
>
> 확인할 내용: 교육 대상은 누구인가요? 교육 주제와 예정일이 정해져 있나요?
>
> 현재 정보로 진행할 때의 가정: 확정 날짜 대신 준비 시작일을 기준으로 일정을 제안합니다.

피드백 정책:

- 핵심 보완 질문은 최대 3개로 제한하고, 이미 답한 내용을 반복해서 묻지 않는다.
- 질문에는 관련 입력 필드와 확인이 필요한 이유를 포함한다.
- 선택 정보 누락을 일괄적으로 생성 차단 사유로 사용하지 않는다.
- 해결되지 않은 항목은 모르는 정보 또는 사용자가 확인한 가정으로 명시한다.
- 보완 질문의 답변과 수정 내용은 최종 입력에 포함하고 사용자에게 변경 내용을 보여준다.
- AI가 사용자의 목표·해야 할 일·제약조건을 확인 없이 덮어쓰지 않는다.
- 검토 실패 시 재시도를 제공한다. 실패를 검토 완료나 사용자 확인으로 간주하지 않는다.

## 입력 평가와 모델 추천

### 평가 축

| 평가 축 | 판단 기준 |
| --- | --- |
| 입력 명확성 | 목표, 대상, 해야 할 일, 완료 조건의 명확성 |
| 전문지식 요구도 | 특정 분야 지식, 기술·표준 이해의 필요 수준 |
| 추론·계획 복잡도 | 선후 관계, 조건 분기, 대안 비교, 상충 제약 조율 |
| 작업 규모 | 대상, 산출물, 실행 항목과 예상 단계의 범위 |

각 축은 0~4단계, 근거, 판단에 부족한 정보를 반환한다. 입력 명확성은 높을수록
명확하다는 의미이며 다른 축의 높은 값과 혼동하지 않는다. 구체적인 단계별 예시와
평가 rubric은 구현 첫 단계에서 고정하고 버전을 부여한다.

점수는 AI 추정치다. 판단할 수 없는 축은 값 없음과 이유를 기록하고, 정보 부족을
높은 복잡도로 바꾸거나 숫자를 임의로 채우지 않는다. 보완 전·후 평가를 각각 보존한다.

### 추천 정책

규칙 기반 특징 추출 → AI 의미 평가 → 서버 추천 정책 → 사용자 모델 선택 순서로 처리한다.

- 항목 수와 제약의 구조 등 계산 가능한 특징은 규칙으로 추출한다.
- AI는 평가 축과 근거를 반환하고, 서버 정책이 허용된 모델 중 추천 모델을 결정한다.
- 초기에는 경제형·균형형·고품질형에 대한 설명 가능한 규칙을 사용한다.
- 모델별 역할과 우선순위는 서버 설정으로 관리한다. 미등록 모델의 성능을 임의로 추정하지 않는다.
- 추천에 사용한 허용 모델 목록, 정책 버전, 평가 근거를 저장한다.
- 불명확한 입력은 보완을 권하며 추천의 판단 한계를 표시한다.
- 사용자가 선택한 모델을 자동으로 덮어쓰지 않는다.
- 작업 난도와 품질·비용·응답 속도 선호는 구분한다. 기존 성공 기준의 `빠른 실행`은
  계획의 실행 속도일 수 있으므로 AI 응답 속도 선호로 바로 해석하지 않는다.

### AI 호출 구성

- 검토용 모델은 서버의 별도 설정으로 관리하고 실제 검토 품질을 확인해 선택한다.
- 생성용 모델은 최종 확인 단계에서 사용자가 선택한 허용 모델이다.
- 기본 흐름은 검토 1회와 생성 1회다. 명시적인 재검토·재시도는 추가 호출이다.
- 타이핑마다 AI를 호출하지 않는다. 완료된 검토는 같은 입력에 대해 재사용할 수 있다.
- 기존 Planning Prompt 평가 작업은 다른 데스크톱의 변경을 먼저 확인·동기화한다.
  검토 prompt와 rubric은 별도 버전으로 관리해 기존 실험과 중복 수정하지 않는다.
- 확인된 가정은 별도 입력 변환 계층을 통해 생성 workflow에 전달한다.
  변환 계층에도 버전을 기록해 실제 생성에 반영한 문맥을 추적한다.

## 데이터 저장 설계

기존 PostgreSQL에 아래 영역을 추가한다. 최종 테이블·컬럼명은 계약 구현 시 확정한다.

| 테이블 제안 | 주요 데이터 |
| --- | --- |
| `planning_reviews` | 프로젝트, 부모 검토 ID, 입력 스냅샷·식별값, 피드백·질문·가정, 점수·근거, 추천 모델, 허용 목록과 검토·추천 정책 버전 |
| `planning_decisions` | 선택 또는 최종 확인 종류, 관련 검토 ID, 실제 선택 모델, 추천 수락·변경 여부, 확인한 입력·가정·모델, 시각 |
| `ai_execution_runs` | 검토·생성 구분, 검토·확인 ID, 실행 모델, 실행 상태·시각·경과 시간, 사용량, 추정 비용·요율 버전, 오류 코드, 결과 ID |
| `planning_quality_evaluations` | 결과·실행 ID, 평가 출처, 평가 기준 버전, 만족도·평가 점수·의견, 비교 평가의 연결 정보 |

연결 관계:

`입력 검토 → 사용자 확인 → 생성 실행 → planning_results → 품질 평가`

저장 원칙:

- 보완 후 재검토는 새 검토 기록을 만들고 부모 ID로 연결한다. 과거 스냅샷을 덮어쓰지 않는다.
- 검토 중 사용자가 실제로 확정한 모델 변경도 기록한다. 생성하지 않고 나간 경우도 조회할 수 있다.
- 최종 확인은 변경 불가능한 입력·가정·선택 모델 스냅샷을 가진 결정 기록이다.
  선택 이벤트와 확인 이벤트를 구분하고 확인 이벤트의 ID를 생성 요청에 사용한다.
- 검토 호출과 생성 호출의 사용량·시간·비용을 각각 기록한다.
- 추정 비용은 사용량과 요율 버전으로 계산한다. 사용량·요율을 모르면 값 없음으로 저장한다.
  청구서로 확인한 실제 비용과 동일한 값으로 표시하지 않는다.
- 정상 생성 결과는 기존 `planning_results`에 저장하고 실행 기록에서 연결한다.
- 편집·복원 버전은 기존 출처 연결을 유지하며 새 AI 실행이나 추천 수락으로 집계하지 않는다.
- 과거 결과에 검토 이력이 없으면 이력 없음으로 표시한다. 임의의 확인 기록을 만들지 않는다.
- 사용자 OK는 입력·가정으로 진행하는 데 대한 확인이다. 결과 품질의 정답 라벨로 사용하지 않는다.
- 원문은 필요한 스냅샷에 저장하고 일반 오류 로그에 전체 입력·credential을 복제하지 않는다.

## API 제안

| 메서드·경로 | 역할 |
| --- | --- |
| `POST /projects/{project_id}/planning-reviews` | 입력 스냅샷 검토·저장, 평가·추천 반환. 재검토 시 부모 검토 ID 전달 |
| `GET /projects/{project_id}/planning-reviews` | 프로젝트 검토 이력 조회 |
| `GET /projects/{project_id}/planning-reviews/{review_id}` | 검토 상세와 연결된 선택·확인·실행 조회 |
| `POST /projects/{project_id}/planning-reviews/{review_id}/decisions` | 모델 선택 또는 최종 확인 저장, 최종 확인 시 확인 ID 반환 |
| `POST /projects/{project_id}/planning-confirmations/{confirmation_id}/generate` | 확인된 스냅샷으로 생성하고 결과·실행 이력 연결 |
| `GET /projects/{project_id}/ai-execution-runs/{run_id}` | 통신 오류·새로고침 후 실행 상태 조회 |
| `POST /projects/{project_id}/planning-results/{result_id}/quality-evaluations` | 사용자 품질 피드백 저장 |

검토·최종 확인 계약은 `packages/shared`와 API schema에 정의한다. 서버는 프로젝트,
검토, 확인, 실행, 결과의 소속 관계와 선택 모델의 현재 허용 여부를 검증한다.

기존 프로젝트 생성 API와 비프로젝트 `/planning/generate`는 평가 스크립트·테스트 등의
사용처를 조사한 뒤 호환 정책을 확정한다. 새 사용자 화면의 생성·재생성·재시도 경로는
확인 ID를 사용한다. 프로젝트 생성 경로를 확인 없이 우회할 수 있게 남기지 않도록 검증한다.
기존 직접 생성 실행은 검토를 거친 실행과 구분해 기록한다.

## 상태와 사용자 확인 보장

Web 흐름: `입력 중 → 검토 중 → 검토 완료 → 최종 확인 → 생성 중 → 생성 완료`.
검토 실패, 생성 실패, 입력 변경으로 인한 검토 만료를 별도 상태로 관리한다.

- 서버가 정규화한 입력으로 식별값을 만들고, 사용자가 확인한 내용과 생성 입력을 검증한다.
- 목표·상황·해야 할 일·제약조건·가정 등 생성에 영향을 주는 내용을 바꾸면 검토·확인을 만료시킨다.
  재검토 요청을 자동 실행하지 않고 사용자에게 재검토 동작을 제공한다.
- 모델만 변경하면 의미 검토는 유지할 수 있지만 기존 최종 확인을 재사용하지 않는다.
- 실행은 현재 mutable Draft가 아니라 확인 스냅샷에서 생성한다. Draft 자동 저장과 분리한다.
- 새로고침 후 최신 Draft와 검토 스냅샷을 비교해 복원하며, 불일치하면 과거 검토로 표시한다.
- 프로젝트 이동·입력 변경 이후 도착한 오래된 응답이 현재 화면을 덮어쓰지 않게 한다.
- 확인·생성 요청에는 멱등성 키를 적용한다. 같은 실행의 재전송은 기존 실행·결과를 반환한다.
- 실패 후 명시적으로 다시 실행하면 동일한 확인에 새 시도 기록을 연결할 수 있다.
  실행 여부가 불명확한 timeout은 상태 조회로 확인하기 전 중복 생성하지 않는다.
- 실행 상태 저장은 짧은 transaction으로 처리하며 외부 AI 대기 동안 DB 잠금을 유지하지 않는다.
- 검토 중에는 별도 상태 안내를 표시한다. 기존 생성 애니메이션은 실제 계획 생성에만 사용한다.
- 검토·생성 실패 시 기존 결과, 선택, 캔버스 위치, 미저장 편집을 보존한다.
- 기존 미저장 편집 확인, 과거 버전 열람, 저장 충돌·복원 동작을 유지한다.

## 이력 화면과 향후 평가

- 프로젝트별 `검토·추천 이력`에서 최초 입력, 보완 검토, 모델 선택과 생성 여부를 조회한다.
- 생성 결과에서 해당 결과의 검토·확인·실행 기록으로 이동한다.
- 추천 수락률, 생성 성공률, 시간·사용량과 사용자 품질 평가는 서로 다른 지표로 관리한다.
- 모델 간 품질 향상은 동일한 최종 입력·가정·출력 조건을 사용한 비교 평가에서 측정한다.
- 피드백 전·후 효과를 비교할 때는 입력과 사용 모델의 차이도 기록해 해석한다.
- 선택 이력이나 미생성 이력만으로 특정 모델이 우수하거나 나쁘다고 학습하지 않는다.

## 구현 순서

1. 평가 rubric, 입력 정규화, Shared/API 계약과 기존 API 호환 정책을 확정한다.
2. Alembic migration과 검토·결정·실행·평가 repository를 구현한다.
3. 별도 AI 검토 provider·prompt와 서버 추천 정책, 사용량 수집을 구현한다.
4. 최종 확인 검증, 멱등성, 생성 workflow 연결과 상태 조회를 구현한다.
5. Web 검토·보완·확인 화면, 모델 선택, 오류 복구와 프로젝트 이력을 구현한다.
6. 자동 검증과 PostgreSQL·브라우저 E2E, 실제 모델 smoke test를 수행한다.

## 완료 기준과 검증

- 상황·해야 할 일이 비어 있어도 주제로 검토를 받을 수 있고, 필요한 보완 질문을 표시한다.
- 명확한 입력에는 불필요한 질문을 반복하지 않고 검토 후 확인·생성할 수 있다.
- 짧고 전문적인 요청과 길지만 단순한 요청을 구별하는 대표 사례를 평가한다.
- 점수·추천 이유·정책 버전이 저장되고, 서버 허용 목록 밖의 모델을 추천·실행하지 않는다.
- 사용자 보완·확인·모델 변경 이력이 누락되지 않으며 미생성 이력도 조회할 수 있다.
- 확인 전 생성, 다른 프로젝트 확인 사용, 입력 수정 후 이전 확인 재사용을 차단한다.
- 확인된 가정이 실제 생성 입력에 포함되고 결과에서 추적 가능하다.
- 더블클릭·재전송·timeout·새로고침·실패 재시도에서 실행과 결과가 중복되지 않는다.
- 검토·생성 사용량과 추정 비용을 구분하고, 누락된 사용량을 0으로 오인하지 않는다.
- PostgreSQL migration·저장·복원과 기존 버전 편집·충돌 처리의 회귀 검사를 통과한다.
- Shared/Web typecheck, 관련 Web·API·AI 테스트, lint·production build 및 브라우저 E2E를 통과한다.
- 실제 모델 smoke test로 검토 구조, 최종 확인, 생성 연결을 검증한다.

## 구현 착수 시 확정할 세부 사항

- 단계별 평가 rubric과 초기 추천 임계값, 모델별 서버 프로필.
- 검토용 모델, timeout·재시도 제한과 입력·출력 크기 제한.
- 기존 직접 생성 API·평가 도구의 호환 방식과 검토 없는 실행의 구분.
- 실행 중 서버 종료에 대한 상태 정리·재시도 정책과 비용 요율 관리 방식.
- 다른 데스크톱에서 진행한 Prompt 평가 변경의 동기화 상태.

이 항목들은 구현 과정에서 코드·테스트 근거와 함께 갱신한다. 학습 기반 추천은
현재 휴리스틱을 비교 기준으로 유지하고 충분한 평가 데이터가 확보된 후 진행한다.
