# AI 입력 피드백 및 모델 추천 구현 로드맵

작성일: 2026-11-24

상태: 로컬 구현과 통합 검증 완료. 다른 환경의 Prompt 평가 변경 동기화는 확인 대기.

- 설계 기준: [AI 입력 피드백 및 모델 추천 설계](ai-input-review-and-model-recommendation-design.md)
- 전체 작업 우선순위: [루트 개발 계획](../dev_plan.md)
- 이 파일은 단계별 작업, 의존 관계, 완료 기준과 검증 결과를 관리한다.
- 날짜를 고정한 일정 대신 각 단계의 완료 조건을 충족한 뒤 다음 단계로 진행한다.
- 체크박스는 해당 산출물과 검증 근거가 확보됐을 때 완료 처리한다.

## 목표 사용자 흐름

`입력 → AI 검토 → 피드백 확인·보완 → 모델 선택 → 사용자 확인 → 계획 생성 → 이력·품질 피드백`

1차 완료 시 사용자는 주제만으로 검토를 시작하고, AI의 질문·진행 가정·추천 모델을
확인한 다음 계획을 생성할 수 있다. 검토·선택·확인·실행 기록은 기존 PostgreSQL에
저장하고 결과 버전과 연결한다.

## Phase 0. 기존 작업과 호환 범위 확인

- [ ] 다른 데스크톱·브랜치의 Prompt 평가 작업을 확인하고 필요한 변경을 먼저 동기화한다.
- [x] 기존 사용자 변경을 보존하면서 구현용 feature branch를 준비한다.
- [x] 프로젝트·비프로젝트 생성 API를 호출하는 Web, 평가 스크립트, 테스트를 조사한다.
- [x] Draft 자동 저장, 결과 버전·복원·충돌 처리, 생성 실패·재시도 흐름을 확인한다.
- [x] 검토 prompt의 별도 버전 관리 범위와 기존 직접 생성 API의 호환 방식을 기록한다.

완료 기준: 중복 수정할 작업이 식별되고, 새 확인 경로로 이전할 호출과 기존 평가용
호출의 처리 방식이 정리돼 있다. 확인되지 않은 외부 작업을 동기화 완료로 표시하지 않는다.

## Phase 1. 평가 기준과 데이터·API 계약 확정

- [x] 입력 명확성, 전문지식 요구도, 추론·계획 복잡도, 작업 규모의 0~4단계 기준을 정의한다.
- [x] 판단 정보 부족은 값 없음으로 표현하고, 단계별 근거·대표 입력 예시를 정한다.
- [ ] 명확한 입력, 모호한 입력, 짧고 전문적인 입력, 길고 단순한 입력,
  상충 제약, 보완 전·후 입력을 포함한 검증 fixture를 준비한다.
- [x] 질문 최대 3개, 질문 대상 필드, 진행 가정과 최종 입력 반영 규칙을 확정한다.
- [x] 검토용 모델 설정, 서버 모델 프로필, 초기 추천 규칙과 정책 버전을 정의한다.
- [x] 작업 난도·계획 성공 기준·모델 응답 속도·비용 선호를 구분한다.
- [x] Shared 타입·런타임 검증과 API schema에 검토·결정·실행·평가 계약을 정의한다.
- [x] 입력 정규화·식별값, 확인 만료, 모델만 변경한 경우, 생성·재시도 상태를 정의한다.
- [x] 검토·생성 timeout, 요청 크기, 멱등성 키와 중복 실행 처리 계약을 정한다.

완료 기준: 같은 fixture의 평가·입력·확인 계약이 Web·API·AI에서 일치하고,
기존 직접 생성 API의 호환 정책이 문서화돼 있다.

검증: Shared 검증과 API schema 테스트, 대표 fixture의 형식·경계값 검사.

## Phase 2. PostgreSQL 이력 저장 기반

- [x] `planning_reviews`, `planning_decisions`, `ai_execution_runs`,
  `planning_quality_evaluations`에 대한 모델과 Alembic migration을 구현한다.
- [x] 프로젝트·검토·확인·실행·결과 연결, 조회용 인덱스와 멱등성 제약을 추가한다.
- [x] 입력 스냅샷·평가·질문·가정·추천 정책과 허용 모델 목록을 저장한다.
- [x] 선택 이벤트와 최종 확인 이벤트를 구분하고 확인 스냅샷의 변경을 차단한다.
- [x] 재검토를 부모 검토 ID로 연결하고 생성하지 않은 선택 이력도 조회한다.
- [x] 검토·생성 실행 상태, 사용량·경과 시간, 추정 비용·요율 버전·오류를 저장한다.
- [x] 사용량·요율을 모르면 값 없음으로 저장하고 품질 평가 출처·기준 버전을 분리한다.
- [x] 검토 목록·상세, 실행 상태, 품질 피드백의 repository와 API 기반을 구현한다.

완료 기준: 실제 PostgreSQL에서 이력 전체를 저장·조회할 수 있고 기존 프로젝트·결과를
계속 읽을 수 있다. 과거 결과에는 검토 이력을 임의로 생성하지 않는다.

검증: migration 적용, repository round-trip, 프로젝트 간 참조 차단, 중복 키·스냅샷 보존 검사.

## Phase 3. AI 입력 검토와 서버 모델 추천

- [x] 별도 구조화 응답 모델과 검토 provider·prompt를 구현하고 버전을 기록한다.
- [x] 규칙 기반 특징과 AI 의미 평가를 결합해 목표 요약·질문·가정·평가 근거를 반환한다.
- [x] 주제만 있는 입력을 허용하고 이미 제공한 정보를 재질문하지 않도록 검증한다.
- [x] 검토 점수를 서버 모델 프로필에 연결해 추천 모델·이유·판단 한계를 생성한다.
- [x] 현재 허용 목록 밖의 모델을 추천하지 않고 사용자의 명시적 선택을 보존한다.
- [x] 검토 API에 부모 검토 연결, 상태 저장, 잘못된 응답·오류 처리를 연결한다.
- [x] 검토·생성 provider의 응답 사용량과 실제 실행 모델·시간 수집을 구현한다.
- [x] 명시적 재검토와 같은 요청 재전송을 구분하고 타이핑 시 자동 호출을 방지한다.

완료 기준: fixture 기반 API 호출로 유효한 검토·추천·실행 기록이 함께 저장되고,
불명확함을 곧바로 높은 난도로 해석하지 않는다.

검증: 검토 출력 형식·질문 수, 정보 부족, 짧은 전문 입력, 상충 제약, 허용 모델 변경,
사용량 누락·provider 실패에 대한 AI·API 테스트.

## Phase 4. 사용자 확인과 계획 생성 연결

- [x] 최종 입력·가정·모델을 고정하는 확인 API를 구현한다.
- [x] 확인 ID로 생성하고 서버가 프로젝트 소속·입력 식별값·현재 허용 모델을 검증한다.
- [x] 입력 수정 시 확인을 만료시키고 모델만 바꾸면 새 최종 확인을 받도록 한다.
- [x] 사용자 확인 가정을 버전이 있는 변환 계층에서 생성 workflow에 전달한다.
- [x] 생성 실행과 기존 `planning_results`를 연결하고 성공·실패 상태를 보존한다.
- [x] 동시 요청·더블클릭·재전송에서 같은 실행·결과를 반환하도록 한다.
- [x] timeout·서버 종료 등 실행 상태가 불명확한 경우의 조회·복구 정책을 구현한다.
- [x] 실패 후 명시적 재시도는 새 실행 기록으로 남기고 자동 모델 변경을 하지 않는다.
- [x] 기존 생성 API·평가 도구의 호환 정책을 적용하고 확인 우회 여부를 검증한다.

완료 기준: 확인 전 또는 다른 입력의 확인으로 생성할 수 없고, 확인한 스냅샷·가정과
선택 모델이 실제 생성에 반영된다. 같은 시도의 재전송은 중복 결과를 만들지 않는다.

검증: API·workflow 연결, 확인 만료, 프로젝트 혼용, 동시 생성, 통신 실패·재시도,
기존 버전 편집·복원·충돌 처리 회귀 검사.

## Phase 5. Web 검토·보완·확인 및 이력 화면

- [x] 입력 패널의 첫 동작을 `AI 입력 검토`로 변경하고 주제만으로 진입하게 한다.
- [x] 검토 중·완료·실패·만료 상태를 Zustand와 API client에 연결한다.
- [x] 목표 요약·질문·가정·추천 근거와 모델 선택 화면을 구현한다.
- [x] 답변·수정 내용이 최종 입력에 반영된 것을 표시하고 명시적 재검토를 제공한다.
- [x] `현재 정보로 진행`과 `확인하고 계획 생성`을 구현한다.
- [x] 서버 추천을 표시하고 모델 선택·변경 이벤트를 기록한다.
- [x] 입력 변경과 프로젝트 이동 후 오래된 응답을 무시하고 새로고침 상태를 복원한다.
- [x] 검토·생성 오류에 재시도·상태 조회를 제공하고 기존 결과·미저장 편집을 보존한다.
- [x] 검토에는 별도 상태 안내를, 실제 생성에는 기존 애니메이션을 표시한다.
- [x] 프로젝트별 검토·추천 이력, 생성 결과의 관련 이력 연결과 품질 피드백 UI를 추가한다.
- [x] 키보드 조작·초점 복귀와 모바일 화면 배치를 확인한다.

완료 기준: 사용자 화면에서 검토부터 확인·생성·이력 조회까지 이어지고, 생성하지 않은
검토·선택도 조회된다. 입력 수정 후 이전 확인으로 생성하지 못한다.

검증: Web 상태·상호작용 테스트와 fixture 기반 브라우저 E2E, 데스크톱·모바일 화면 확인.

## Phase 6. 통합 검증과 1차 완료

- [x] Shared/Web typecheck, 관련 Web·API·AI 테스트, lint·production build를 통과한다.
- [x] 실제 PostgreSQL에 migration을 적용하고 검토→확인→생성→결과 연결을 검증한다.
- [x] 입력 부족·보완·가정 수락·모델 변경·재생성 시나리오를 브라우저 E2E로 검증한다.
- [x] 중복 요청·확인 만료·timeout·새로고침·실패 복구와 이력 연결을 검증한다.
- [x] 기존 노드·연결·로드맵 편집, 버전 복원·저장 충돌, 화면 위치 보존을 회귀 검증한다.
- [x] 실제 검토용 모델과 허용 생성 모델의 smoke test로 출력·연결·사용량을 확인한다.
- [x] 테스트·실제 모델 검증 결과와 한계를 `docs/reports`의 구현 보고서에 기록한다.
- [x] 설계 문서, 사용 안내, 루트 개발 계획과 이 로드맵의 상태를 최종 구현에 맞춰 갱신한다.

완료 기준: 위 검증 근거를 확보하고 설계 문서의 1차 완료 기준을 모두 충족한다.
실행하지 못한 실제 모델 검증은 미완료로 남기고 전체 완료로 표시하지 않는다.

## 후속 단계 — 데이터 기반 추천 고도화

1차 완료 이후 별도 범위로 진행하며 필수 구현과 구분한다.

### 후속 A. 동일 입력의 모델 비교

- [ ] 같은 최종 입력·가정·출력 조건으로 비교할 대표 사례를 선정한다.
- [ ] 동일 평가 기준으로 모델별 결과 품질·응답 시간·토큰·비용을 기록한다.
- [ ] 추천 수락·사용자 OK와 실제 품질 점수를 구분해 평가한다.
- [ ] 비교 결과로 초기 추천 규칙·모델 프로필을 조정하고 이전 정책과 비교한다.

### 후속 B. 대시보드와 학습 기반 추천

- [ ] 모델별 품질·비용·추천 효과를 비교하는 화면의 필요성을 검토한다.
- [ ] 충분한 비교 데이터와 라벨을 확보하고 데이터 선정·익명화·분리 기준을 정한다.
- [ ] 현재 추천 정책을 baseline으로 유지하며 분류·순위 모델을 평가한다.
- [ ] GPU가 필요한 학습은 별도 데스크톱·브랜치에서 수행한다.
- [ ] 품질·비용 균형 개선을 검증한 후 제한적으로 적용하고 기존 정책 복귀 경로를 유지한다.
