# 향후 개발 리마인드

이 문서는 현재 구현 범위를 넘어 향후 검토하거나 개발해야 할 작업을 한곳에
모아두기 위한 리마인드다. 완료 여부의 최종 기준은 코드, 테스트, PR 이력이며,
작업을 시작할 때는 별도 이슈나 개발 계획으로 범위와 완료 기준을 구체화한다.

## 장기 보류 — GPU 데스크탑 작업

### 모델 추천 알고리즘 학습 기반 고도화

이 작업은 현재 개발 환경에서 바로 진행하지 않는다. 실제 사용·평가 데이터가
충분히 쌓인 뒤 GPU가 있는 다른 데스크탑에서 별도 브랜치와 실험 환경을 구성해
진행한다. 그 전까지는 현재 점수 기반 휴리스틱을 baseline으로 유지한다.

현재 모델 추천은 Planning Brief의 입력 길이, 항목 수, 계획 유형, 중요 기준을
점수화하는 휴리스틱이다. 빠르고 설명 가능하지만 계획 내용의 실제 의미와
난이도는 판단하지 못한다. 충분한 데이터가 쌓이면 학습 기반 추천으로 교체하거나
휴리스틱과 함께 사용하는 방식을 검토한다.

착수 전 준비:

1. 추천 시점의 Planning Brief, 허용 모델, 휴리스틱 점수와 추천 결과를 기록한다.
2. 사용자가 실제 선택한 모델과 추천 수락·변경 여부를 수집한다.
3. 생성 성공 여부, 응답 시간, 토큰 사용량, 예상 비용을 모델별로 기록한다.
4. 계획 결과 품질을 공통 평가 기준으로 채점하고 사람의 피드백을 함께 저장한다.
5. 개인정보와 민감한 계획 내용은 익명화하거나 학습 데이터에서 제외한다.

학습·평가 단계:

1. 휴리스틱을 baseline으로 고정하고 추천 정확도와 생성 품질을 측정한다.
2. 계획 복잡도와 적합 모델에 대한 라벨 기준을 정의한다.
3. 먼저 작은 분류기 또는 ranking 모델로 실험하고, 필요할 때만 LLM 기반
   분류나 fine-tuning을 검토한다.
4. 학습·검증·테스트 데이터를 프로젝트나 사용자 단위로 분리해 데이터 누수를
   방지한다.
5. 품질, 비용, 지연시간을 함께 반영한 오프라인 평가를 통과한 모델만 shadow
   mode와 제한된 사용자 실험으로 검증한다.
6. 새 추천기가 기존 baseline보다 나쁘면 즉시 휴리스틱으로 돌아갈 수 있게 한다.

완료 기준:

- 동일한 대표 데이터셋에서 휴리스틱보다 품질·비용 균형이 개선된다.
- 추천 이유를 사용자에게 설명할 수 있다.
- 서버 허용 목록 밖의 모델을 추천하지 않는다.
- 추천은 사용자의 명시적 모델 선택을 강제로 덮어쓰지 않는다.

## 우선순위 A — 가까운 후속 작업

### 모델별 실제 품질·비용 평가

- Luna, Terra, Sol, Mini를 동일 대표 입력으로 비교한다.
- 구조 일관성, 계획 실행 가능성, 응답 시간, 토큰, 실제 비용을 기록한다.
- 평가 결과를 바탕으로 기본 모델과 추천 점수 임계값을 조정한다.
- 생성 이력과 모델별 품질·비용을 비교하는 대시보드를 검토한다.

### 실제 환경 E2E 보강

- 계획 생성 후 새로고침했을 때 DB 결과와 Planning Brief가 복원되는지 확인한다.
- 허용 모델별 실제 OpenAI 생성 smoke test를 수행한다.
- 과거 결과 열람, 복원, 새 버전 생성까지 브라우저 E2E로 검증한다.

> Prompt 평가 및 Prompt 버전 관련 작업은 다른 데스크탑에서 진행 중인 변경을
> 먼저 동기화한 뒤 이어간다. 그 전에는 관련 코드, 데이터셋, 보고서를 중복
> 수정하지 않는다.

## 우선순위 B — 제품 기능 고도화

### 모델 정책

- 프로젝트별 기본 모델을 현재 Draft 선택값과 구분해 명시적으로 저장한다.
- 관리자 역할 기반 모델 허용 정책과 조직별 비용 한도를 검토한다.
- 모델별 안내 정보가 실제 평가 결과와 어긋나지 않도록 갱신 절차를 마련한다.

### 계획 결과 편집

- Graph node와 dependency edge 수동 편집
- drag 위치와 layout 저장
- Roadmap 단계 inline 편집과 순서 변경
- 편집본과 AI 생성 원본의 버전 이력 및 복원
- 이미지, PDF, Markdown 내보내기
- 고급 편집이 필요할 때 tldraw SDK 도입 검토

### 사용자와 협업

- 사용자 인증
- project ownership과 권한 분리
- 프로젝트 공유와 공동 편집
- 변경 이력, 충돌 처리, 감사 로그

## 우선순위 C — 플랫폼 확장

### 지식 활용

- 파일과 기존 프로젝트 자료를 참조하는 RAG pipeline
- Vector DB 도입 필요성 및 데이터 보존 정책 검토
- 출처 표시와 오래된 지식 갱신 전략

### 배포와 운영

- 배포 환경 구성과 release 절차
- API·AI workflow observability
- 오류율, latency, token, 비용 모니터링과 알림
- migration 및 장애 복구 runbook
- secret 관리와 환경별 접근 정책

### 문서화

- Product requirement document
- MVP user flow와 UX research notes
- AI workflow 및 추천 정책 문서
- Release notes
- Deployment runbook

## 기술 부채 및 정기 확인

- Next.js가 고정하는 PostCSS 8.4.31과 Sharp 0.34.x의 upstream 안전 버전을
  정기적으로 확인하고 호환 버전이 나오면 audit 경고를 해소한다.
- 의존성 업데이트 시 Shared typecheck, Web test·lint·build, API test와 실제
  persistence smoke test를 함께 실행한다.
- 추천 규칙의 점수와 임계값은 실제 평가 데이터 없이 임의로 계속 조정하지 않는다.

## 작업 시작 체크리스트

- 기존 문서와 다른 브랜치에서 이미 진행 중인 작업인지 확인한다.
- 독립된 feature branch를 만든다.
- 데이터·API·UI 계약과 완료 기준을 먼저 정의한다.
- 개인정보, 비용, 외부 API 호출 범위를 확인한다.
- 자동 테스트와 실제 환경 smoke test 범위를 정한다.
- 구현 후 이 문서에서 완료된 항목을 제거하거나 완료 이력 문서로 이동한다.
