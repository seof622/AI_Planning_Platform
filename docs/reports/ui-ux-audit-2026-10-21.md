# 플랜노트 UI/UX 검토 — 2026-10-21

현재 화면에서 가장 먼저 개선할 부분은 저장 방식의 설명, 결과를 읽는 경험,
작성·검토·편집 사이의 전환이다. 이번에 도구 위치를 나누면서 계획 입력의 접근성은
개선했지만 여러 작업이 동시에 열려 있고, 저장 상태와 생성 조건을 사용자가 추측해야 한다.

## 검토 범위와 근거

- 현재 `feature/workspace-layout-reorganization`의 코드와 직전 브라우저 검증 캡처를 확인했다.
- 화면 크기는 1440×960, 1024×768, 390×844다.
- 이번 조사 시점에는 연결 가능한 브라우저가 없어서 새로운 실시간 조작을 수행하지 않았다.
- 외부 제품은 공식 도움말·디자인 설명을 조사했다. Linear, Notion, Figma, VS Code는
  공식 문서에 포함된 이미지도 내려받아 직접 비교했다.
- 아래의 사용성 영향과 우선순위는 검토자의 판단이다. 사용자 테스트로 입증한 결과나
  접근성 적합성 심사 결과는 아니다.
- 조사 결과를 기록했으며 이번 조사에서는 제품 코드를 변경하지 않았다.

## 우선순위 1 — 저장과 생성 동작을 이해할 수 있게 만들기

### 1. 저장 버튼의 이름과 실제 저장 범위가 다르다

확인한 동작:

- 그래프의 **그래프 새 버전 저장**, 로드맵의 **로드맵 새 버전 저장**, 노드 편집기의
  **편집본 새 버전 저장**이 모두 같은 `saveGraphEdits`를 호출한다.
- 이 함수는 현재 노드·연결·로드맵 전체를 새 버전으로 저장한다.
- 요구사항과 Planning Brief는 별도로 자동 저장한다.
- 헤더의 **저장된 상태**는 `graphEditStatus`를 바탕으로 표시한다.

사용성 판단: 사용자는 각 버튼이 해당 영역만 저장한다고 예상할 수 있다. 입력 초안의 자동 저장과
결과 편집의 명시적 저장도 하나의 상태처럼 읽힌다.

제안:

- 공통 버튼을 **변경 내용 새 버전으로 저장**으로 통일한다.
- 가까이에 **노드·연결·로드맵 편집 전체 저장**이라고 범위를 설명한다.
- **입력 초안 자동 저장 중/저장됨/실패**와 **결과 편집 미저장**을 따로 표현한다.
- 입력 변경 뒤에는 **현재 입력은 아직 결과에 반영되지 않았습니다**라고 표시하고,
  기존 결과가 있을 때 생성 버튼을 **새 버전으로 다시 생성**으로 구체화한다.

확인 기준: 노드와 로드맵을 함께 수정했을 때 저장 대상과 다음 생성의 효과를 화면에서 설명할 수 있다.

코드 근거: `PlanningWorkspace.tsx`, `planningStore.ts`의 `saveCurrentPlanningBrief`, `saveGraphEdits`.

### 2. 계획 생성 버튼이 비활성화된 이유를 알려주지 않는다

확인한 동작: 프로젝트·모델·계획 주제·상황·할 일이 있어야 버튼이 활성화된다.
주제 외의 필수 입력 표시나 부족한 항목을 알려주는 설명은 없다.

사용성 판단: 주제만 입력한 사용자는 무엇을 더 해야 하는지 찾기 어렵다.

제안: 필수 항목을 표시하고 버튼 가까이에 **해야 할 일을 1개 이상 입력해 주세요**처럼
현재 부족한 항목을 안내한다. 첫 화면에는 간단한 입력 예시를 적용할 수 있는 버튼을 둔다.
장기적으로는 주제만으로 시작할 수 있는지 API 계약과 함께 검토한다.

확인 기준: 비활성화된 버튼을 보고 남은 입력을 식별할 수 있다.

코드 근거: `RequirementPanel.tsx`의 `canSubmit`.
참고: [버튼 상태 안내](https://www.nngroup.com/articles/button-states-communicate-interaction/).

### 3. 로딩·빈 상태·실패 후 복구가 구체적이지 않다

확인한 동작:

- 여러 요청이 같은 `loading` 상태를 사용하며 캔버스는 **생성 중**으로 표시한다.
- 빈 상태에는 **그래프 없음 / 계획을 생성하세요**를 표시한다.
- 새 생성이 실패하면 메모리의 `planningResult`를 `null`로 설정하여 기존 결과가 화면에서 사라진다.

사용성 판단: 결과 조회와 생성이 구별되지 않고 긴 생성 중에는 기다려야 하는지 판단하기 어렵다.
재생성 실패 후 기존 결과를 다시 찾는 작업도 생긴다.

제안: **프로젝트 불러오는 중**, **AI가 계획을 생성하는 중**을 구분하고 경과 시간을 표시한다.
빈 화면은 첫 입력·예시 계획으로 이어지게 한다. 재생성 오류는 기존 결과를 유지한 채
원인과 재시도 동작을 제공한다. 실제 진행 정보를 받지 않는 상태에서는 임의의 진행률이나
완료 예상 시간을 표시하지 않는다.

코드 근거: `StatusView.tsx`, `planningStore.ts`의 `generateResult`, `selectProject`, `selectPlanningResult`.
참고: [복잡한 앱의 빈 상태 설계](https://www.nngroup.com/articles/empty-state-interface-design/).

## 우선순위 2 — 결과를 읽고 수정하는 화면 구성

### 4. 로드맵이 모든 단계의 편집 양식을 동시에 보여준다

확인한 화면: 단계마다 제목 입력·설명 입력·관련 노드·선행 단계·속성·이동·삭제가 표시된다.
전체는 가로로, 각 카드는 세로로 스크롤한다. 1024×768에서는 카드의 하단 속성을 한눈에 볼 수 없다.

사용성 판단: 실행 순서와 핵심 내용을 훑어보는 데 편집 양식이 시선을 분산시킨다.

제안: 기본 화면은 **단계 번호·제목·설명 요약·우선순위·선행 관계**를 읽는 리스트로 만든다.
단계를 선택하면 오른쪽 상세 패널에서 편집한다. 지금의 가로 카드는 선택 가능한 보기로 유지할 수 있다.
노드와 단계의 상세 편집기는 Figma의 선택 기반 속성 패널 패턴을 참고한다.

확인 기준: 단계 10개를 입력창을 건드리지 않고 순서대로 읽을 수 있고, 선택한 단계만 상세 편집한다.

코드 근거: `RoadmapPanel.tsx`, `globals.css`의 `.roadmap__steps`, `.roadmap-step`.

### 5. 그래프와 로드맵의 화면 비율이 고정되어 있다

확인한 화면·코드: 로드맵이 기본 340px을 차지하며 작은 데스크톱에서는 280px이다.
계획 입력 패널도 항상 열려 있다. 그래프를 넓게 보거나 로드맵만 읽는 전환은 없다.

제안: 상단에 **전체 / 그래프 / 로드맵** 보기를 제공하고 입력 패널을 접을 수 있게 한다.
분할선으로 높이를 조절하고 설정을 기억한다. VS Code·Obsidian의 배치 조절을 참고하되
자유로운 창 도킹 전체를 구현하는 범위까지 늘릴 필요는 없다.

확인 기준: 노트북에서 그래프나 로드맵 하나를 화면의 주된 작업 영역으로 확대할 수 있다.

### 6. 생성 결과를 설명하는 제목과 요약의 비중이 낮다

확인한 화면: 본문은 **구조 캔버스**, **로드맵**이라는 도구 이름으로 시작한다.
결과 요약은 **버전 정보·비교** 창 안에 있다. 결과가 이미 있어도 입력 양식이 계속 큰 비중을 차지한다.

제안: 생성 후에는 프로젝트명 아래에 결과 요약과 현재 버전을 보여주고 검토를 시작하게 한다.
입력은 **계획 입력 수정**으로 다시 열 수 있게 한다. Linear의 프로젝트 개요처럼
결과의 의미를 먼저 전달한다. 새 프로젝트에서는 반대로 입력을 우선한다.

### 7. 그래프와 로드맵을 연결해서 탐색하기 어렵다

확인한 동작: 관련 노드 참조는 로드맵에 저장되어 있지만, 노드를 선택해도 관련 단계가
같이 강조되지 않는다. 캔버스에는 이름으로 노드를 찾는 검색 UI가 없다.

제안: 노드를 선택하면 관련 단계를 강조하고, 단계에서 관련 노드를 누르면 해당 노드로
이동한다. 노드 수가 늘어날 때 이름 검색과 유형 필터를 제공한다.

확인 기준: 사용자가 “이 단계가 어느 구성 요소를 다루는지” 화면 이동 없이 확인할 수 있다.

### 8. 편집을 되돌리는 조작과 화면 위치의 연속성이 부족하다

확인한 코드: 저장 버전 복원은 있지만 로컬 Graph·Roadmap 편집 전체를 대상으로 한
실행 취소/다시 실행 UI는 없다. 노드 수나 캔버스 크기가 바뀌면 `fitView`를 호출한다.

사용성 판단: 저장 전 실수를 일부만 되돌리기 어렵고, 확대해 보던 위치가 편집 중에 바뀔 수 있다.

제안: 노드·연결·단계 편집의 실행 취소/다시 실행을 제공한다. 새 결과 진입 시 자동 맞춤을
적용하고 일반 편집·패널 열기에서는 가능한 한 사용자의 확대율과 중심을 유지한다.
**전체 보기** 버튼으로 언제든 다시 맞춘다. Miro의 실행 취소와 탐색 도구를 참고한다.

## 우선순위 3 — 탐색과 세부 표현

### 9. 정보의 크기·대비·우선순위를 더 분명히 나눌 필요가 있다

확인한 화면·코드: 보조 정보와 도구에 9–12px 텍스트가 많고,
여러 버튼·라벨이 비슷한 회색으로 표현된다. 그래프는 화면 맞춤 과정에서 글자가 더 작게 보인다.
단계 이동 버튼은 25px 크기다.

제안: 주요 읽기 텍스트와 보조 정보를 구분해 키우고 상태·선택·일반·비활성의 차이를 강화한다.
반복되는 **PLAN BRIEF / PLAN OVERVIEW** 같은 장식 라벨은 줄인다.
데스크톱의 작은 도구와 터치 환경의 누르기 영역도 별도로 점검한다.
이 검토만으로 색 대비나 터치 영역의 접근성 기준 통과 여부를 단정하지 않는다.

### 10. 프로젝트·버전 선택을 실제 내용 중심으로 만들면 좋다

확인한 코드: 최초 로딩 시 프로젝트 목록의 첫 항목을 선택한다. 현재 선택을 다시 복원하는 처리는 없다.
버전은 긴 날짜·출처 문자열을 네이티브 선택창에 표시하며 좁은 화면에서는 일부가 잘린다.

제안: 마지막 프로젝트를 복원하고 목록이 늘면 검색·최근 프로젝트를 제공한다.
버전은 **v8 · 현재**, **v7 · 로드맵 수정**처럼 짧게 구분하고 시간·모델·상세 변경은
별도 이력 패널에서 읽게 한다. 긴 비교 작업에는 작은 팝업보다 넓은 패널을 제공한다.

## 제안하는 화면의 작업 흐름

1. **처음 작성:** 주제·필수 입력과 예시, 생성 조건을 우선한다.
2. **결과 검토:** 결과 제목·요약을 읽고 그래프 또는 로드맵 보기를 선택한다.
3. **세부 편집:** 항목 선택 → 오른쪽 편집 → 공통 저장 상태 확인 → 새 버전 저장.
4. **이력 확인:** 필요한 때 버전 이력·변경 비교를 열고 닫는다.

- 저장 범위·초안 저장 상태·생성 조건 안내(항목 1·2)를 구현했다.
- 구현과 검증 범위는 [저장·생성 안내 보고서](save-generation-guidance-implementation-report.md)에 기록한다.
- 로딩·실패 복구(항목 3)는 [로딩·복구 보고서](loading-recovery-implementation-report.md)의 범위로 구현했다.
- 다음 우선순위는 로드맵 읽기 보기와 선택 기반 상세 편집(항목 4)이다.

## 권장 진행 순서

1. 저장 범위·초안 상태와 생성 조건 안내를 먼저 정리한다.
2. 로드맵을 읽는 보기와 선택 기반 상세 편집을 추가한다.
3. 그래프·로드맵 집중 보기, 입력 패널 접기와 크기 조절을 추가한다.
4. 실행 취소, 관련 항목 강조, 검색과 마지막 작업 위치 복원을 이어간다.

제품 기능을 추가하기 전에 다음 짧은 사용성 확인을 권장한다: 처음 온 사용자가 계획을 생성하고,
로드맵의 한 단계를 수정한 뒤 저장 범위를 설명하고, 관련 노드를 찾아 실수를 되돌릴 수 있는지 본다.
완료 시간이나 성공률의 개선 수치는 실제 비교 검증 후 기록한다.
